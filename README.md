# ECG1.2 — гибридный дигитайзер ЭКГ

Модульный пайплайн дигитизации ЭКГ: **картинка бумажной распечатки → цифровой
сигнал 12×N**. Собирается из лучших открытых решений, каждое подключается как
изолированный модуль.

> [!WARNING]
> **⚠️ Это learning/demo-инструмент, НЕ медицинское изделие.**
> Результаты не предназначены для диагностики, лечения или любых клинических
> решений. Не используйте на реальных пациентских данных для медицинских целей.

---

## Архитектура

Пайплайн — цепочка логических стадий. Каждая стадия — отдельный модуль в `src/`
с единой сигнатурой:

```python
run(input_path: str, config: dict) -> output_path: str
```

Выход одной стадии = вход следующей. Оркестратор `src/pipeline.py` читает
`configs/pipeline.yml` и вызывает активные стадии по очереди.

| # | Стадия        | Вход → Выход                                        | Источник подхода |
|---|---------------|-----------------------------------------------------|------------------|
| 1 | `preprocess`  | фото/скан → выровненная нормализованная картинка    | OpenCV (свой)    |
| 2 | `layout`      | картинка → раскладка отведений (где какое)          | Ahus-AIM/Open-ECG-Digitizer |
| 3 | `segment`     | картинка → бинарная маска кривой ЭКГ                | felixkrones/ECG-Digitiser (nnU-Net) |
| 4 | `calibrate`   | маска+картинка → масштаб (px→мВ, px→с) + угол        | felixkrones/ECG-Digitiser (Hough) |
| 5 | `vectorize`   | маска+калибровка → сырой сигнал по отведениям        | свой (+ masoudrahimi39 для наложений) |
| 6 | `reconstruct` | сырой сигнал → полные 10с × 12 отведений            | UMMISCO/ecgtizer |
| 7 | `output`      | сигнал → WFDB/.npy + превью-график                  | свой             |

### Принципы

- **Изоляция зависимостей.** Внешние модели с конфликтующими требованиями
  подключаются как **отдельные подпроцессы**, каждый со своим venv. Обмен
  данными — через **файлы** (`.npy` / WFDB / JSON), а не через общие импорты.
- **Мягкая деградация.** Падение одной стадии не роняет весь пайплайн: ошибка
  логируется, вход прокидывается дальше без изменений.
- **Конфиг рулит.** Какие стадии активны, пути и параметры — в
  `configs/pipeline.yml` (флаг `enabled` у каждой стадии).

## Установка (ядро)

Ядро (оркестратор + препроцессор) использует собственный venv:

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install pyyaml numpy opencv-python-headless matplotlib
```

Внешние модели (felixkrones, ecgtizer, …) ставятся в свои venv в соответствующих
фазах — см. ниже. Они **намеренно** не в одном окружении с ядром.

### Ядро felixkrones (Фаза 1)

- Окружение: conda-env `ecgdig` (Python 3.11 + torch + nnU-Net), путь прописан в
  `configs/pipeline.yml → interpreters.segment_calibrate`. Вызывается **подпроцессом**
  (`python -m src.run.digitize`), обмен через WFDB-файлы, без общих импортов.
- Веса: M3 (`fold_all/checkpoint_final.pth`, ~453 МБ). На GitHub у репо felixkrones
  **исчерпан LFS-бюджет**, поэтому веса берутся из локальной копии
  `~/ECG-Digitiser/models/M3` (симлинк в `external/`), и в `weights/`-политику не
  попадают. Если у тебя весов нет — их нужно получить из релиза/зеркала проекта.
- Синтетика в «родном» формате генерируется встроенным `ecg-image-generator`
  (см. `tools/make_native_wfdb.py` + `tools/gen_native_image.py`).
- nnU-Net на CPU ≈ 8 мин/картинка, поэтому результат **кэшируется** по содержимому
  входа (`output/cache/<hash>/`).

### Реальные фото (Фаза 2)

`src/preprocess/` приводит фото/скан к виду, близкому к синтетике ядра:
grayscale-детекция листа → `warpPerspective` → удаление теней делением на
размытый фон → обрезка полей → апскейл до 2200px. Панель «до/после»
(`before_after.png`) кладётся в папку стадии.

**Тонкость с поворотом.** Ядро felixkrones перед сегментацией оценивает угол
через Hough (`get_rotation_angle`); на реальных сканах низкого разрешения сетка
не даёт ≥1200 голосов → угол **NaN** → `rotate(NaN)` обнуляет картинку → пустой
сигнал. Мы **не правим их код**, а вызываем ядро через свой драйвер
`tools/felixkrones_safe_digitize.py`: он переиспользует их функции
(сегментация/векторизация/WFDB) дословно, но при NaN-угле берёт 0° (фото уже
выпрямлено в preprocess).

**Диагноз и фикс качества на реальных фото.** Первая версия давала плохой
результат: felixkrones-nnU-Net присваивает отведение по абсолютной позиции на
своей синтетической странице, и на реальном фото (другие пропорции/разрешение)
**путает, какое отведение где** — метки «переворачиваются» по вертикали, II
налезает на всё (проверено визуально на IMG_4074; геонормализация под эталон не
помогла — значит дело в самой модели, не в позиции).

Решение — **layout-aware реконструкция** с НЕЗАВИСИМЫМ анализом каждого
отведения, встроенная в пайплайн:
- `segment` отдаёт СЫРУЮ маску nnU-Net (метки игнорируем, берём как «где чернила»);
- `layout` находит 4 строки (по проекции маски) и 4 колонки, назначает отведения
  по шаблону 3×4+ритм, а затем для КАЖДОГО отведения считает **своё** окно поиска
  (центр строки ± доля до соседней строки) и **свою** базовую линию (мода
  гистограммы y) — соседи не влияют друг на друга, устойчиво к вертикальному
  смещению отведений внутри строки;
- `vectorize` трассирует каждое отведение независимо «следованием» за ближайшим
  кластером (устойчиво к глубоким S и толщине штриха), где маска дырявая —
  подхватывает тёмные пиксели полутона рядом с траекторией, разрывы интерполирует
  и не останавливается, дрейф базовой линии снимает скользящей медианой (чинит
  длинную ритм-строку). Ритм-строка анализируется отдельно. Каждому отведению
  проставляется **покрытие** (cov%) как индикатор надёжности.

Итог на IMG_4074: отведения назначены верно, изолиния на нуле, амплитуды
физиологичны; хорошо читаются II/aVR/aVL/aVF/V2/V5 и др., а лиды с разреженной
маской (I/V3/V6) честно помечены низким cov. Overlay раскладки и превью сигнала
кладутся в папки стадий `layout/` и `vectorize/`.

### Разные раскладки (Фаза 3)

Раскладка не захардкожена — шаблоны в `configs/lead_layouts.yml` (схема как у
Ahus-AIM/Open-ECG-Digitizer: `grid` из строк; строка с одинаковыми отведениями =
ритм-строка). Поддерживаемые форматы, у каждого своя папка с примером в
`data/samples/formats/<формат>/` (`sample.png` + `reconstructed.png` + README):

| формат | строк×колонок | описание |
|--------|---------------|----------|
| `3x4`    | 3×4 | 3×4 без ритма |
| `3x4_1R` | 4×4 | 3×4 + ритм II (стандарт) |
| `3x4_3R` | 6×4 | 3×4 + 3 ритма (V1, II, V5) |
| `6x2`    | 6×2 | 6×2 без ритма |
| `6x2_1R` | 7×2 | 6×2 + ритм II |
| `12x1`   | 12×1 | каждое отведение 10с |

Стадия `layout` определяет число строк по покрытию цветовых чернил (фит-скоринг,
работает и на бледных фото) и назначает отведения по шаблону; дальше — та же
независимая per-lead трассировка. Рендер строит результат в ИСХОДНОЙ раскладке.

**Выбор формата:** `template: auto` в `pipeline.yml` (best-effort авто-детект,
надёжен на 3×4/12×1) или явно — флагом `--template <формат>` / вторым аргументом
`./run_ecg.sh фото.jpg 6x2_1R`. Для гарантии на нестандартных сканах задавайте
формат явно.

> Численный замер качества — **Фаза 5**.

С телефона в той же сети Wi-Fi — по адресу, который сервер печатает при запуске

```bash
tools/share.sh          # печатает публичный адрес https://xxxxx.lhr.life
```

Адрес живёт, пока скрипт запущен, и он **публичный**: кто угодно, кому он
попадёт, сможет загружать картинки, пока туннель открыт.

Открой в браузере, загрузи картинку ЭКГ, выбери формат раскладки (или «авто»).
Что получишь:

- **цифровую копию** плёнки — линия построена по данным, геометрия исходника
  сохранена;
- **сигнал 12 отведений** в CSV;
- **измерения**: ЧСС, длительность зубца P, PQ, QRS, QT/QTc, оси зубца P,
  комплекса и зубца T, уровень ST и индекс Соколова — вместе с усреднёнными
  комплексами всех отведений, на которых видно, куда поставлены границы;
- **все показатели одним куском JSON**, с кнопкой «скопировать» — чтобы отдать
  их другой программе или чату. Оговорки о надёжности лежат внутри вместе с
  числами: без них получатель разберёт интервалы как показания прибора и не
  узнает, что плёнка читалась плохо;
- **проверки доверия**: мелкий снимок, недочитанные строки плёнки, несходимость
  связей между отведениями, нераспознанный формат, расхождение калибровочного
  импульса с сеткой. Не прошло — красная плашка с причиной, а не тихая
  выдача правдоподобного мусора.

## Точность оцифровки

Проверка на **PTB-XL**: берём запись с точно известным сигналом, печатаем из неё
плёнку, прогоняем конвейером и сравниваем с оригиналом (`tools/validate_ptbxl.py`,
40 записей, 478 отведений).

| | |
|---|---|
| корреляция формы | 0.988 |
| общий масштаб | 1.009 |
| **высота зубца R** | **0.990** — 98% отведений в пределах 5% |
| SNR | 15.9 дБ |
| ЧСС | ошибка 0.0 уд/мин, 98% записей в пределах 5 |

Высота зубца R вынесена отдельно от общего масштаба намеренно. Трассировщик
движка ведёт линию по центру тяжести чернил в колонке, а у острой вершины в
колонку попадает и восходящий, и нисходящий склон — вершина срезается тем
сильнее, чем она острее. По корреляции и SNR это не видно совсем, но клинические
пороги (гипертрофия, критерии инфаркта) заданы именно высотой зубца. Недобор
был 13.7%; после восстановления вершин по карте вероятностей движка — 1.0%.
Общий масштаб при этом считается наименьшими квадратами, а не отношением
разбросов: шум оцифровки сам поднимает разброс и «усиление» получалось больше
единицы даже там, где амплитуды переданы верно.

## Измерения: PQ, QRS, QT/QTc, ось, ST, индекс Соколова

`tools/ecg_delineate.py` считает по оцифрованному сигналу то же, что печатает
на ленте настоящий кардиограф.

Границы ищутся **сразу по всем отведениям**, а не по одному. Деполяризация
начинается в один момент во всём сердце, но в отдельном отведении её начало
может прийтись на изолинию и быть невидимым — вектор в этот момент направлен
поперёк оси отведения. Поэтому строится пространственная скорость

```
sv(t) = sqrt( sum_i (dx_i/dt)^2 )
```

по восьми **линейно независимым** отведениям (I, II, V1–V6). Остальные четыре —
арифметика от первых двух, и включать их значило бы трижды посчитать одно и то
же, перекосив sv во фронтальную плоскость.

Конец зубца T — методом касательной: в точке самого крутого спада проводится
касательная, её пересечение с изолинией и есть конец. Так делают потому, что
«место, где кривая легла» у пологого зубца определяется шумом и гуляет на сотню
миллисекунд, а точка максимальной крутизны устойчива.

Ось — по алгебраической сумме зубцов в I и aVF, с поправкой `aVF/(√3/2)`:
усиленные отведения меряют проекцию в масштабе √3/2 от двухполюсных, и без
деления ось врёт до 4° — на границе нормы это меняет вывод.

### Насколько это точно

Эталон — **PTB-XL+**: для тех же записей выложена разметка двух независимых
медицинских анализаторов, University of Glasgow и GE 12SL. Данные качаются
одной командой:

```bash
tools/fetch_ptbxl.sh 40
```

Проверка в два этапа, иначе не понять, чья ошибка:

```
этап A: эталонный сигнал -> измерения           = ошибка алгоритма разметки
этап B: эталонный сигнал -> плёнка -> движок
                         -> измерения           = ошибка всей цепочки
```

Правая колонка — **насколько расходятся между собой сами анализаторы** на этих
же записях. Это и есть масштаб: требовать от себя большего, чем они сходятся
друг с другом, бессмысленно.

Медиана модуля ошибки; в скобках — доля записей в пределах допуска
(P 20 мс, PQ 20 мс, QRS 12 мс, QT 25 мс, ось QRS 15°, оси P и T 25°).

| | A: алгоритм | B: вся цепочка | Glasgow против GE 12SL |
|---|---|---|---|
| P       | 8 мс (87%)  | 11 мс (76%)     | 6 мс (85%) |
| PQ      | 8 мс (92%)  | 9 мс (92%)      | 4 мс (100%) |
| QRS     | 4 мс (90%)  | 4 мс (90%)      | 4 мс (95%) |
| QT      | 6 мс (89%)  | 7 мс (86%)      | 4 мс (90%) |
| ось QRS | 2.7° (97%)  | 3.3° (92%)      | 2.0° (100%) |
| ось P   | 5.0° (97%)  | 5.2° (89%)      | 7.0° (100%) |
| ось T   | 2.8° (94%)  | 4.3° (89%)      | 5.0° (90%) |
| ЧСС     | 0.7 уд/мин  | 0.9 уд/мин      | 0 |
| ST      | 8 мкВ       | 13 мкВ          | — |

40 записей PTB-XL, `tools/validate_measure.py`.

Читать так: **QRS, оси и ЧСС переживают оцифровку без потерь** — расходимся с
Glasgow ровно настолько, насколько Glasgow расходится с GE, а по осям зубцов P
и T даже теснее, чем анализаторы между собой. QT, PQ и длительность P чуть хуже.

### Зубец P: находимость отдельно от точности

Точность интервала PQ сама по себе обманчива. Если зубец P не найден, запись в
сравнение не попадает вовсе — а выпадают как раз трудные записи, и от их потери
статистика **улучшается**. Поэтому потери считаются отдельно, а специально для
замера ложных срабатываний записи без зубца P изготавливаются: в наборе таких
нет, поэтому зубец стирается (`--specificity`) — прямой вставкой на его место
плюс шум того же участка.

| | было | стало | между анализаторами |
|---|---|---|---|
| находимость на эталонном сигнале | 97% | **98%** | 100% |
| находимость после оцифровки      | 83% | **95%** | — |
| длительность P, эталон           | −14 мс (77%) | **0 мс (87%)** | +3 мс (85%) |
| длительность P, после оцифровки  | −14 мс (61%) | **−5.5 мс (76%)** | — |
| ложные срабатывания              | — | **3%** | — |

Терялись не мелкие зубцы, а те, рядом с которыми **крупный зубец T**. Порог
кандидата брался в долях размаха окна поиска, а размах задаёт хвост зубца T
предыдущего удара — при ЧСС от 80 он попадает в окно, и настоящий зубец P до
45% высоты чужого зубца T просто не дотягивал. Вторая беда сидела в опоре для
порога границы: она бралась как минимум всего окна, а он лежит **за** вершиной
этого зубца T. Порог, отсчитанный от такой опоры, ниже неё, и поиск начала
спокойно проходил сквозь: длительность выходила 295–298 мс, и запись
отбраковывалась как невозможная.

Теперь горб ищется по **выпуклости** — насколько он поднялся над своими
окрестностями; что творится в другом конце окна, её не касается. А опора у
каждой границы своя и ближайшая к вершине.

Отдельно: начало, упёршееся в край окна поиска, не принимается. Видно только
продолжение горба за границу, и интервал PQ выходил равен ширине окна — не
измерение, а её отпечаток. Так ловится дотянувшийся до края чужой зубец T:
из пяти ложных срабатываний три давали PQ 338–340 мс при пределе окна 340.

Два измеренных отказа, оставлены в коде комментариями, чтобы не пробовать
заново: требование к **ширине** горба (находимость падает с 40 записей до 34,
ложных срабатываний не убавляет — scipy меряет ширину на половине выпуклости, а
у зубца P на спаде зубца T она куда меньше самого зубца) и порог различимости
**0.2 мм** вместо 0.4 (одна находка, шесть ложных).

Признак «зубец P есть» берётся по названной анализатором длительности, а не по
его флагу `P_Found_Global`: на пяти записях набора Glasgow ставит флаг в ноль,
но тут же выдаёт и длительность зубца, и интервал PQ, а второй анализатор ставит
единицу. Все пять — тахикардия 127–151, где зубец P наезжает на зубец T.

Оговорки, без которых цифры врут:

- Плёнка печатается **своим рендером** — чистая, без бликов, смятия и
  перспективы. Это верхняя граница; на фотографии будет хуже.
- Конец зубца T приведён к определению Glasgow постоянной поправкой +16 мс:
  метод касательной по построению даёт конец раньше, чем «возврат к изолинии».
  Поправка снимает ровное смещение, разброс от неё не меняется.
- В раскладке 3×4 отведения сняты **не одновременно**, общего времени у них
  нет, и комплексы приходится совмещать по всплеску энергии QRS. Цена этого
  измерена отдельно, на том же эталонном сигнале: QRS 4 → 5 мс, ось 2.7 → 2.8°,
  PQ, QT и ЧСС без изменений. То есть совмещение по энергии комплекса работает
  почти так же, как общее время.
- Сомнительные измерения помечаются, а не прячутся: QTc за пределами 300–600 мс,
  ненайденный зубец P, ненайденный конец зубца T, меньше трёх ударов в среднем
  комплексе, меньше шести отведений в пространственной скорости. Отдельно
  отбраковываются отведения, у которых удар встал мимо остальных: если быстрого
  движения в комплексе почти нет, значит линия прочиталась с разрывом или в
  клетку попал кусок соседа. Такое отведение исключается из расчёта границ и из
  таблицы ST, а на картинке помечается.
- Индекс Соколова (S в V1 + R в V5 или V6, порог 35 мм) держится целиком на
  высоте зубцов, поэтому он же служит прямой проверкой восстановления вершин:
  занижение амплитуды на 10% двигает индекс на 3–4 мм — как раз через порог.

## Дорожная карта (фазы)

- **Фаза 0** — каркас: структура, оркестратор, стадии-заглушки (passthrough). ✅
- **Фаза 1** — ядро felixkrones/ECG-Digitiser (segment + calibrate), прогон на синтетике. ✅
- **Фаза 2** — OpenCV-препроцессор реального фото (перспектива, тени, обрезка). ✅
- **Фаза 3** — шаблоны раскладок отведений (Open-ECG-Digitizer). ✅
- **Фаза 4** — достройка отведений до 10с (UMMISCO/ecgtizer).
- **Фаза 5** — валидация на PTB-Image (MSE, корреляция Пирсона).
- **Фаза 6** (опц.) — разделение наложенных трасс (masoudrahimi39/ECG-code).

Текущий статус — см. коммиты; каждая фаза завершается отдельным коммитом.
